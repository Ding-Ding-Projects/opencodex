# Feature completeness inventory

**65 contracts. 9 complete, 31 partial, 24 absent, 1 not applicable.**

That is 14% done. More than a third of what this file lists has no code behind it at all — not a
disabled switch, not a stub, not a route nobody wired up. Absent means nothing exists.

Audited **2026-08-13** against `c8fd307f` on the primary checkout. Eight read-only agents, one per
slice, each reading source rather than trusting a prior report; one row (local version history) was
then downgraded from complete to partial on a re-check, and the reason is recorded in that row.

## Why this file is hand-written

A checklist that enumerates only what it found cannot detect a feature that was never built. It
scans the tree, discovers eleven things, reports eleven things, and is silent about the fifty-four
it never knew to look for. That silence reads as completeness. This file therefore names every
canonical contract **including the ones with no implementation**, so that a missing feature has a
row with the word `absent` in it rather than no row at all.

Three consequences follow, and they are the whole point:

- **"Optional" describes a user's runtime choice, never an implementation exemption.** A narrator
  that ships disabled by default is shipped. A narrator that does not exist is absent. The
  distinction is not rhetorical: this repository has one of each.
- **A contract is not satisfied by a sibling surface having it.** The desktop app having a colour
  picker does not give the documentation site one. Two surfaces, two rows, two verdicts.
- **A contract that genuinely cannot apply names itself and its reason.** There is exactly one such
  row here (forge publishing), and it carries the exact clause and the exact reason. A gap with no
  note reads as an oversight to the next reader and as a decision to nobody.

### This file exists because the last count was wrong

`ROADMAP.md` recorded six features as missing that had shipped, and left them recorded that way for
two weeks. The re-check on 2026-08-13 struck five of those entries through and rewrote a sixth.
The failure was not laziness; it was that a status written once and never re-derived is a claim
about the past wearing the present tense. This file is only worth reading if it is uncomfortable,
so nothing here is rounded up and nothing is marked done on the strength of a plan.

### Status vocabulary

| Status | Means |
| --- | --- |
| `present` | The contract is met on every surface it governs. Reached and operated, not inferred from a filename. |
| `partial` | Something real ships and a named half does not. The **Missing** column says exactly which half. |
| `absent` | Nothing exists. Searched and not found; the searches are recorded in the row. |
| `n/a` | The contract is textually conditional and its condition does not hold here. The clause and the reason are named. |

`partial` is not a softer `present`. A feature whose engine is complete and whose call sites are
empty — the narrator, for instance — is partial, and the reason a user gets silence is in the row.

## The largest absent items are unbuilt products, not missing switches

Twenty-four rows say `absent`. They are not twenty-four evenings of work, and treating them as a
checklist of toggles is how this number stays where it is. Grouped by what actually has to be built:

**Three are applications in their own right.** The **universal file converter** with its eight
adapter categories, bundled-and-proven offline adapters, sandboxed bounded execution and unlimited
resumable queue; the **PDF tool set** with post-write reopen validation; and the **local Ollama
suite manager** with an exhaustive paginated catalogue, evidence-backed hardware-fit verdicts, a
batch pull queue, a full chat surface and allowlisted harness launch with snapshot and rollback.
Each is a product with its own subsystem, its own failure taxonomy and its own test matrix. The
Ollama row is the one most likely to be misread as nearly done, because the word "ollama" already
appears in the provider registry — that is a base URL, and it is no part of this.

**One is a browser extension plus a download manager.** The **capture flow** needs an extension that
does not exist, three surfaces that do not exist, and an always-on-top window capability that the
Electron main process has never used (`alwaysOnTop` returns zero hits in the entire checkout).

**One is a security-theatre suite of four interlocking pieces.** **Toy locks** on every rendered
element, each with its own credential; the **anchored lock wizard**; **Support Tickets** as the
recovery desk; and the **built-in authenticator** with RFC 6238 verification. Beneath all four sits
a dependency none of them can be built without: **there is no OS credential vault integration
anywhere in this codebase.** `safeStorage`, `keytar`, `wincred` and `DPAPI` return zero hits, and
the one credential the GUI persists goes to browser storage under a documented exception. The QR
renderer is the single piece already done and it is done well — reuse `gui/src/lib/qr.ts` rather
than rebuilding it.

**Two are cross-cutting infrastructure that touch every surface at once.** The **command palette**
needs an index over commands, pages, settings and appearance controls, live controls rendered inside
result rows, and a teleport that opens the owning surface, selects the right tab, reveals the
element, focuses it and highlights it — reaching into every screen in the app. **School mode** and
the **personal-vocabulary upload** both need a shared cross-application data record with a live
watcher, because both are defined as propagating to a running app without a restart; neither is a
setting that can live in `Prefs`.

**Two are a scheduling engine and a network boundary.** **Scheduled settings** needs a rule schema,
a timezone and DST story, deterministic precedence and history recording. **External settings
sources** needs a privileged HTTPS boundary with SSRF protection, allowlisted fields and bounded
refresh — plus, again, the credential vault.

**Three are narrower but still real.** The **destructive super-confirmation gate** (two keys, a
slider, two animations, an emergency exit and its full test matrix); the **in-app documentation
browser** (a bundler step, a renderer, a route, in-app link resolution, a search and a build-failing
completeness check); and **context-menu keyboard shortcuts**, which needs a binding registry that
both registers the handlers and supplies the display strings, because deriving the display from
anywhere else is how a menu comes to advertise a key that does nothing.

**Two are identity work with a trap in them.** The **app rename** and **app-logo customization** are
both display-only by contract, and both are dangerous precisely there: a rename that reaches the
data directory orphans every stored profile, and a custom mark that reaches package identity breaks
the update feed. The work is mostly in proving the decoupling, not in drawing the control.

### And the partials hide two structural holes

Neither is a feature, and both will keep producing `absent` rows if they are left alone:

- **The documentation site is a second product held to the same contract and has roughly half of
  it**, guarded by a `check-dist.mjs` that asserts two things and would pass on a site with none of
  it. Its 18 test files are not run by the root test script or by CI at all.
- **Coverage guards are list-shaped in three places and absent in most.** `every-search-bar-has-a-builder.test.ts`
  and `collection-search-flags.test.ts` are the right shape and are the reason two slices have
  precise numbers rather than impressions. There is no such list for rich controls, for settings
  explanations, for dropdown filters, for menu shortcuts, for M3 conformance, or for the contract as
  a whole — and a rule without a list passes cleanly on a surface that never adopted it.

## Keeping this file honest

- **Re-derive a row before re-dating it.** A status is a claim about the tree at a commit. Carrying
  it forward untouched is how `ROADMAP.md` came to record six shipped features as missing for two
  weeks.
- **A row moves to `present` when the contract is met on every surface it governs**, not when the
  first surface has it. Two surfaces, two verdicts.
- **Never delete a row.** A feature nobody has built still needs its row saying so; that is the only
  thing separating this file from a checklist that cannot see what is not there.
- **`CHANGELOG.md` is generated from release tags and is never hand-edited.** Feature status belongs
  here; release history belongs there.
