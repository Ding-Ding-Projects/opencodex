## Why this file is hand-written

A checklist that enumerates only what it found cannot detect a feature that was never built. It
scans the tree, discovers eleven things, reports eleven things, and is silent about the fifty-four
it never knew to look for. That silence reads as completeness. This file therefore names every
canonical contract **including the ones with no implementation**, so that a missing feature has a
row with the word `absent` in it rather than no row at all.

Three consequences follow, and they are the whole point:

- **"Optional" describes a user's runtime choice, never an implementation exemption.** A narrator
  that ships disabled by default is shipped. A narrator that does not exist is absent. The
  distinction is not rhetorical: this repository has one of each.
- **A contract is not satisfied by a sibling surface having it.** The desktop app having a colour
  picker does not give the documentation site one. Two surfaces, two rows, two verdicts.
- **A contract that genuinely cannot apply names itself and its reason.** There is exactly one such
  row here (forge publishing), and it carries the exact clause and the exact reason. A gap with no
  note reads as an oversight to the next reader and as a decision to nobody.

### This file exists because the last count was wrong

`ROADMAP.md` recorded six features as missing that had shipped, and left them recorded that way for
two weeks. The re-check on 2026-08-13 struck five of those entries through and rewrote a sixth.
The failure was not laziness; it was that a status written once and never re-derived is a claim
about the past wearing the present tense. This file is only worth reading if it is uncomfortable,
so nothing here is rounded up and nothing is marked done on the strength of a plan.

### Status vocabulary

| Status | Means |
| --- | --- |
| `present` | The contract is met on every surface it governs. Reached and operated, not inferred from a filename. |
| `partial` | Something real ships and a named half does not. The **Missing** column says exactly which half. |
| `absent` | Nothing exists. Searched and not found; the searches are recorded in the row. |
| `n/a` | The contract is textually conditional and its condition does not hold here. The clause and the reason are named. |

`partial` is not a softer `present`. A feature whose engine is complete and whose call sites are
empty — the narrator, for instance — is partial, and the reason a user gets silence is in the row.

## The largest absent items are unbuilt products, not missing switches

Eight rows say `absent`, down from twenty-four at the original audit and from sixteen as the last
pass recorded it — though the whole of that last fall is bookkeeping rather than building: all eight
features already existed and the pass that called them absent had read a stale tree (see the second
revision note at the top of this file). They are still not eight evenings of work, and treating them
as a checklist of toggles is how this number stays where it is. Grouped by what actually has to be
built:

**Two are applications in their own right.** The **universal file converter** with its eight
adapter categories, bundled-and-proven offline adapters, sandboxed bounded execution and unlimited
resumable queue; and the **local Ollama suite manager** with an exhaustive paginated catalogue,
evidence-backed hardware-fit verdicts, a batch pull queue, a full chat surface and allowlisted
harness launch with snapshot and rollback. Each is a product with its own subsystem, its own failure
taxonomy and its own test matrix. The Ollama row is the one most likely to be misread as nearly
done, because the word "ollama" already appears in the provider registry — that is a base URL, and
it is no part of this.

**The PDF tool set left this paragraph this pass.** It used to sit beside the converter and Ollama
manager as a third unbuilt application; it is now `partial` on its own row above, with all seven
operations, a bounded sandbox, atomic writes with post-write reopen validation, a GUI page and a CLI
counterpart. What is left of it is reach and rigor, not construction — recorded on its row rather
than repeated here.

**One is a browser extension plus a download manager.** The **capture flow** needs an extension that
does not exist, three surfaces that do not exist, and an always-on-top window capability that the
Electron main process has never used (`alwaysOnTop` returns zero hits in the entire checkout).

**The security-theatre suite is built, and this paragraph used to say it was not.** Toy locks, the
anchored lock wizard, Support Tickets, TOTP registration and the built-in authenticator all ship and
are scored on their own rows above; so is the OS credential vault this paragraph called a dependency
none of them could be built without (`src/lib/os-credential-vault.ts`, Windows DPAPI). The QR
renderer was correctly identified as the one piece already done, and it was in fact reused rather
than rebuilt — `AuthenticatorAddDialog.tsx:318` renders through it. What is left in this area is
reach rather than construction: the locks exist and can only be created on one surface, and the lock
wizard pairs a TOTP factor by printing raw base32 instead of the QR the app already knows how to
draw. Both are half-days against the rows above, not a suite.

**School mode, scheduled settings and external sources are likewise built.** School mode has the
shared cross-application record with the live watcher this paragraph said it needed, because that is
indeed the clause it lives or dies by; scheduled settings has the rule schema, the timezone and DST
story, deterministic precedence and history recording; external sources has the privileged HTTPS
boundary with SSRF protection, allowlisted fields and bounded refresh. Each is `partial` for named
reasons on its own row, and **all eight name the same one: the documentation site is a second product
held to the same contract and has none of them.** For School mode and external settings sources it is
the only substantive reason left. That is worth saying once here rather than eight times above — the
largest single block of remaining work in this file is now one surface, not one feature.

**One is narrower but still real.** **Context-menu keyboard shortcuts** needs a binding registry that
both registers the handlers and supplies the display strings, because deriving the display from
anywhere else is how a menu comes to advertise a key that does nothing. The destructive
super-confirmation gate and the in-app documentation browser used to sit in this paragraph — both now
ship and are scored `present` above.

**Two were identity work with a trap in them.** The **app rename** and **app-logo customization** are
both display-only by contract, and both are dangerous precisely there: a rename that reaches the
data directory orphans every stored profile, and a custom mark that reaches package identity breaks
the update feed. The work is mostly in proving the decoupling, not in drawing the control — which
is exactly what both now score `partial` on rather than `present`: the app rename ships with the
decoupling held by construction (a storage module with no imports, literal storage keys, and a
consumer list that is four display surfaces long) and **no guard asserting it stays that way**.
That is the one row in this file where a missing coverage guard protects against data loss rather
than against a cosmetic regression.

### And the partials hide two structural holes

Neither is a feature, and both will keep producing `partial` rows for as long as they are left alone:

- **The documentation site is a second product held to the same contract and has roughly half of
  it**, guarded by a `check-dist.mjs` that asserts two things and would pass on a site with none of
  it. Its 18 test files are not run by the root test script or by CI at all. This pass made the hole
  considerably more expensive rather than smaller: eight features moved off `absent` and **not one of
  them reached `present`**, every one of them naming this site among its missing halves. Every feature
  the desktop app ships from here arrives as a `partial` by default, because the second surface it is
  owed on is not being built alongside it.
- **Coverage guards are list-shaped in a few places and absent in most.** `every-search-bar-has-a-builder.test.ts`
  and `collection-search-flags.test.ts` were the right shape at the last audit; `dropdown-menu-filter-inventory.test.ts`
  now joins them — a hand-written, named enumeration (`CONVERTED`, `ALREADY_COMPLIANT`, `EXEMPT`,
  each entry naming a real reason) that fails when a listed surface loses its filter, proved by
  deleting the line and watching the named test go red — and is the reason the two dropdown/context-
  menu rows above carry a precise adoption count rather than an impression. There is still no such
  list for rich controls, for settings explanations, for menu shortcuts, for M3 conformance, or for
  the contract as a whole — and a rule without a list passes cleanly on a surface that never adopted
  it. A related but structurally different guard, `docs-articles-complete.test.ts`, closes the same
  blind spot a different way for the documentation browser: not a hand-written surface list but an
  independent second implementation of "which files count," so a bug in the real bundler's exclusion
  rule cannot also hide from the test written to catch it — worth naming as a second reusable pattern
  even though it is not the same shape as the other three.

## Keeping this file honest

- **Re-derive a row before re-dating it.** A status is a claim about the tree at a commit. Carrying
  it forward untouched is how `ROADMAP.md` came to record six shipped features as missing for two
  weeks.
- **A row moves to `present` when the contract is met on every surface it governs**, not when the
  first surface has it. Two surfaces, two verdicts.
- **Never delete a row.** A feature nobody has built still needs its row saying so; that is the only
  thing separating this file from a checklist that cannot see what is not there.
- **`CHANGELOG.md` is generated from release tags and is never hand-edited.** Feature status belongs
  here; release history belongs there.
