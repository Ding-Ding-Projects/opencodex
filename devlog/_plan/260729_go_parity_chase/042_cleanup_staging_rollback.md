# 042 — WP4b: 스테이징과 롤백

선행: 041(판정 계약). 이 문서는 041이 승인한 후보를 **실제로 옮긴다**.
상태: 스테이징/롤백 원시요소 구현 완료. 조율자(`ExecuteArchivedCleanup`)는 043 이후.

## 이 조각의 책임

041은 "무엇을 지울지"를 정했다. 042는 그것을 **격리 디렉터리로 옮기고, 실패하면
되돌린다**. 이 유닛에서 처음으로 사용자 파일이 움직인다.

가장 중요한 성질은 성공 경로가 아니라 **부분 실패**다. 두 파일 중 하나를 옮긴 뒤
실패했을 때 아무도 되돌리지 않으면, 사용자 입장에서는 "실패했다는 메시지"와 함께
파일 하나가 사라진 상태가 된다. 실패보다 나쁘다.

## 오라클 계약

`stageCandidates` (`src/storage/cleanup.ts:1545`):

- 후보의 **물리 파일마다** 스테이지로 rename.
- basename 충돌은 예외. `archived_sessions/`는 현재 평면이지만, 나중에 중첩 구조가
  생겨도 조용히 덮어쓰지 않게 막는다.
- 실패 시에도 **이미 옮긴 목록을 반환**한다. 이게 롤백의 입력이다.

`rollbackStaged` (`:1583`):

- **역순**으로 되돌린다.
- 원위치가 다시 점유돼 있으면 되돌리지 않고 `remaining`에 남긴다 — 사용자가 그 사이
  다시 만든 파일을 덮어쓰지 않는다.
- `remaining`이 비어야만 완전 복구다.

`purgeStaged` (`:1609`): permanent 모드의 삭제.

## 구현 (`go/internal/storage/cleanup_stage.go`)

`StagedFile`은 **재선언하지 않았다**. `restore.go:124`에 같은 `{From, To, RelPath}`가
이미 있고, 복원과 정리는 같은 이동을 반대 방향으로 하는 것이므로 타입이 둘이면 두 경로가
갈라진다.

`StageHooks`로 실패를 주입한다. **한 번도 실행된 적 없는 롤백은 롤백이 아니므로**,
실패 경로가 테스트에서 발화 가능해야 한다:

| 훅 | 무엇을 흉내내나 |
| --- | --- |
| `BlockDestBasenames` | 목적지를 디렉터리로 선점 → 그 파일의 rename 실패 |
| `FailRollbackBasenames` | 되돌리지 못하는 파일 |

`RemoveStageIfEmpty`는 `remaining`이 있으면 스테이지를 **지우지 않는다**. 되돌리지 못한
파일에게 그 디렉터리와 매니페스트는 출처를 아는 유일한 기록이다.

## 활성화 증거 (C-ACTIVATION-GROUNDING-01)

테스트 6종이 모두 파일시스템을 직접 읽어 확인한다:

1. 성공 스테이징 — 원본이 사라지고 스테이지에 생김
2. **주입된 중간 실패 + 완전 롤백** — 두 번째 목적지를 막아 첫 파일이 이미 옮겨진 뒤
   실패시키고, 롤백 후 `archived_sessions` 파일 수가 이전과 **동일**함을 확인
3. 롤백 실패 보고 — 막힌 파일이 스테이지에 남고 `restored=false`
4. **재생성된 원본을 덮어쓰지 않음** — 롤백 전에 원위치에 다른 내용을 쓰고, 롤백 후
   그 내용이 그대로인지 읽어서 확인
5. `remaining`이 있으면 스테이지 보존, 없으면 제거
6. purge가 지우고 실패분을 보고

2번과 4번이 이 유닛의 핵심이다. 둘 다 파일 내용/개수를 **읽어서** 판정하지, 반환값만
믿지 않는다.
