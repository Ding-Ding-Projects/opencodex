# 005 — A 페이즈 감사 1라운드 종합

감사자: 독립 리뷰어 서브에이전트 (read-only, 코드베이스 직접 재확인)
판정: **FAIL** — 블로커 8건(High 5, Medium 2, Low 1)
주 에이전트 조치: 8건 전부 수용. 반박 0건.

## 왜 전부 수용했나

High 5건 중 가장 큰 두 건을 직접 재확인했고 둘 다 사실이었다. 리뷰어가 사실 관계에서
정확했으므로 나머지도 신뢰하되, 각 항목의 **수정 방향**은 내가 결정한다.

## 블로커별 처리

### B1 (High) — `config`를 도움말 전용으로 오분류

**확인함.** TS `src/cli/config-command.ts`는 점 경로, 소스 진단(`--source`), 파일/stdin 검증,
`export`, `--yes` 확인 후 `import`을 지원한다. 비밀 키 마스킹(`SECRET_KEYS` 정규식)과
프로토타입 오염 차단(`BLOCKED_SEGMENTS`)도 있다.

Go `go/internal/cli/config_command.go`는 `path|show|validate|get|set|unset`과 고정 키 몇 개만
지원하며 `export`/`import`가 **없다**.

`002`의 "config는 구현이 아니라 도움말 누락"은 **틀렸다**. 등록되어 있다는 사실이 파리티를
뜻하지 않는다.

→ 조치: `045_cli_config_parity.md` 신설, work-phase `wp4b` 추가.

### B2 (High) — `account` 인증 서브명령 누락

**확인함.** TS `src/cli/account-auth.ts`는 `login`/`reauth`, `code`, `cancel`,
`reset-credits`를 디스패치하고 `/api/codex-auth/login/code`, `/api/oauth/login/code`,
`/api/codex-auth/reset-credits/consume`를 호출한다. stdin 안전 코드 입력과 폴링, `--yes`
보호가 있다.

Go `go/internal/cli/account.go`의 사용법에는 `list|current|use|refresh|auto-switch|alias|
add-key|add|remove`만 있고 인증 서브명령이 **전혀 없다**.

`002`는 `account`를 "Go에 있음"으로 표시했는데, 명령은 있지만 **인증 표면 전체가 빠져
있었다**. 이것이 이 감사에서 가장 위험한 발견이다 — 자격증명 경로가 어느 work-phase에도
속하지 않은 채 완료 선언될 수 있었다.

→ 조치: `046_cli_account_auth.md` 신설, work-phase `wp4c` 추가. `010`의 `--code` 마스킹
원시요소가 여기서 실제로 쓰인다.

### B3 (High) — `/api/models` A안이 거짓 DONE을 허용

타당하다. `004`의 계약은 "Go가 TS와 다르면 Go가 틀렸다"인데, `050`의 A안은 런처를 관대하게
만들어 **서버 발산을 남긴 채** 통과할 수 있게 한다. `120`이 그것을 평범한 잔여로 문서화하면
DONE이 된다 — 계약 위반이다.

→ 조치: A안은 런처 국소 수정으로 유지하되, **서버 응답 형태 차이를 `NEEDS_HUMAN` 파리티
예외로 승격**한다. `120`에서 이 항목이 미해결이면 `DONE`을 막는다. `050`과 `120` 모두 수정.

### B4 (High) — `110`이 개요 수준

타당하다. Kiro 항목은 수용 기준이 아예 없고, 업데이트 항목은 "나중에 대조"에 그친다.
게다가 스코프에서 `go/internal/oauth/**`를 제외해놓고 Kiro 구현이 거기 있다고 지목했다 —
자기모순이다.

→ 조치: `110`을 하위 슬라이스로 분할하고 스코프 모순을 수정. Kiro는 OAuth 표면이므로
별도 슬라이스로 승격.

### B5 (High) — 의존성이 아니라 직렬 일정

타당하다. `030`/`040`/`050`은 실제로는 `010`만 필요하고 서로 독립이다. `002`의
`wp1 → wp2 → wp3 → wp4 → wp5` 표기는 DAG가 아니라 순번이다.

진짜 순서 제약만 남긴다:

```
010 ─┬─> 020
     ├─> 030
     ├─> 040
     ├─> 045
     ├─> 046
     └─> 050

080.1 -> 080.2 -> 080.3 -> 080.4     (각 단계가 앞 단계 산출물 소비)
090.1 -> 090.2                       (릴레이가 이미지 복원의 전제)
060  -> (독립)
070  -> (독립)
100  -> (독립)
110  -> 부분적으로 wp11이 conversationId 필드 소유
130  -> 060의 ACL 작업 이후
```

→ 조치: `002`의 순서 문단을 DAG로 교체.

### B6 (Medium) — 자기 페이즈에서 도달 불가능한 수용 기준

타당하다. `080.1`은 프리뷰만 구현하는데 기준 5가 **적용**을 요구한다. 적용은 `080.2`에
온다. `090.1`도 마찬가지로 이미지 복원을 요구하는데 이미지는 `090.2`다.

이것은 "증거를 미루거나 조작하게 만드는" 형태의 결함이다 — 정확히 이 유닛이 피하려는 것.

→ 조치: `080.1` 기준 5·6을 `080.2`로, `090.1` 기준 9를 `090.2`로 이동.

### B7 (Medium) — goalplan의 1:1 주장이 거짓

타당하다. `wp8a..wp8d` 4개가 문서 `080` 하나를, `wp9a`/`wp9b` 2개가 `090` 하나를 가리킨다.

두 선택지 중 **문서 분할이 아니라 문서 내 하위 슬라이스 유지**를 택한다. 이유: `080`의 네
슬라이스는 하나의 안전성 계약(다이제스트 → 트랜잭션 → 복원 → 정책)을 공유하며, 문서를
쪼개면 그 계약이 흩어진다. 대신 **goalplan의 주장을 사실에 맞게 고친다**: 각 work-phase가
문서의 특정 섹션(`080.1` 등)을 가리키도록 제목에 명시하고, 1:1 주장을 "문서 또는 문서 내
명명된 슬라이스"로 정정한다.

### B8 (Low) — 명령 수 부정확

타당하다. `grok`과 `integration`은 TS에서 별도 디스패치된다. 구현 그룹 10개 / 정규 명령
토큰 11개.

→ 조치: `002` 표에 라벨 정정.
