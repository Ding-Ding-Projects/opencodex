# 130 — wp13: Windows UAC 승격 프로토콜

work-phase: `wp13` · 선행: `060` (ACL 플래너 정리) · 순서 정본: `006`

**보안 리뷰 경계.** 권한 상승, 특권 실행 파일 선택, 롤백, 영속 서비스 상태 정확성.

## 왜 `060`에서 분리했나

`060`의 ACL 순서 수정은 기존 Go 플래너 안에서 명령 순서를 바꾸는 좁은 변경이다. UAC 승격은
**Go에 전혀 없는 것**을 새로 만들고 서비스 설치 트랜잭션까지 바꾼다. 하나로 묶으면 실패 시
상태가 더 나빠진다.

## 오라클 계약

`src/lib/windows-elevation.ts`:

- **단일 UAC 실행 PowerShell 트랜잭션.** 여러 번 UAC 프롬프트를 띄우지 않는다.
- 신뢰된 System32 경로 해석 (PATH 하이재킹 방지)
- 예약 프로토콜 코드 `0/10/11/12/13`
- **UAC 취소 `1223`은 별도로 유지**한다. `1223`을 포함한 알 수 없는 값은 프로토콜 실패로
  분류한다 — 취소와 실패를 뭉개면 안 된다.
- 롤백은 **승격된 프로세스 안에서** 수행한다(두 번째 UAC 프롬프트 없이)
- **TEMP 파일 IPC를 절대 쓰지 않는다** (특권 경계에서 임시 파일은 공격 표면)

## Go 현재

승격 프로토콜이 없다. `taskManager.Install`(`go/internal/service/install.go:98`)이 비특권
`/create` 후 `/run`을 호출한다. create가 성공하고 run이 실패하면 **동일 승격 내 롤백이 없다** —
반쯤 설치된 작업이 남는다.

## 변경

- `go/internal/platform/`에 순수 공용 프로토콜/계획 파일 + `_windows.go` 런처 +
  `!windows` 스텁 추가.
- `ElevatedSchedulerOutcome`, 예약 코드 5종 상수, 알 수 없는 값(1223 포함)을 프로토콜 실패로
  처리하는 분류기, 주입 가능한 런처 인터페이스.
- `install.go:98`을 변경: **분류된 create 접근 거부일 때만** 승격 create/run/delete 트랜잭션
  사용. 결과가 성공이고 사후 조건이 통과할 때까지 설치 성공을 보고하지 않고 호출자 상태도
  지속시키지 않는다.
- 비승격 create/run이 성공하는 일반 경로는 그대로 유지. 실패를 조용히 재시도하지 않고,
  임시 파일 결과 IPC를 쓰지 않는다.

## 비-Windows 테스트 전략

ACL과 동일한 방식이다: 계획·실행을 태그 없는 공용 코드에 두고 `Platform:"windows"` +
주입 러너로 검증한다(`go/internal/platform/winacl_common_test.go:20`이 이미 그렇게 한다).

공용 테스트에서 검증: UAC 스크립트/계획 구성, 결과 분류기, 모의 런처.
실제 `Start-Process -Verb RunAs`, `icacls.exe`, `schtasks.exe` 통합은 Windows 매트릭스로 남긴다.

## 수용 기준

| # | 활성화 | 증거 |
| --- | --- | --- |
| 1 | 성공 경로 | 런처 **1회**만 호출 |
| 2 | 롤백 필요 | 두 번째 UAC 프롬프트 없음 |
| 3 | 모든 경로 | TEMP 파일 쓰기 없음 |
| 4 | 사용자 취소(1223) | 설치 상태 쓰기 없음 |
| 5 | 알 수 없는 종료 코드 | 프로토콜 실패로 분류, 상태 쓰기 없음 |
| 6 | 롤백 실패 | 설치 상태 쓰기 없음 |
| 7 | 타임아웃(불확정) | 조정 절차 수행, 성공 보고 안 함 |
| 8 | 비특권 경로 성공 | 승격 미사용 |

## 터미널 결과 주의

macOS에서는 계획·분류기·모의 런처까지만 증명할 수 있다. **실기 Windows 검증은 호스팅 CI
매트릭스가 필요하므로 이 항목의 최종 상태는 `BLOCKED`가 될 수 있다.** 그 경우 정직하게
그렇게 보고하고 `DONE`이라 부르지 않는다.
